# October 15 security verification

Working-tree review on 2026-10-10, based on `ae5948d55019c6edf9354636e7961a071ca75d50` plus the uncommitted October mission changes. This document describes inspected code, not the promises in onboarding or design documents. The pre-mission backend baseline was 448 passing tests. The final backend run after CA pinning and effective token-expiry display passed 536 tests, skipped one directory-symlink case because this host cannot create that symlink, and emitted one SQLAlchemy deprecation warning in 58.01 seconds. The Windows HTTPS golden path ran and passed. Focused P0, reporting, enrollment, and TLS tests cited below exercise the named paths. No claim is made that the HP Omen and second Windows machine have completed an elevated live installation or LAN run.

## Decision

**Merge judgment: controlled prototype code candidate; no final merge approval yet.** The P0 remote exposure defects identified at the start of the review have been fixed in this working tree, no open Critical or High source-level bypass was found in the inspected paths, and the final backend suite passed. Elevated Windows installation and ACL/DPAPI/NTFS checks must still confirm credential protection on the intended hosts before merge approval. A two-machine HTTPS enrollment, approval, scan, report, revoke, and restart run is required before claiming demo readiness. This is not approval for production deployment: the Medium operational gates below, including offline CA-key custody and PostgreSQL concurrency if that database is used, remain open. A passing suite does not establish hardware and firewall properties.

**Enrollment design safe to implement: yes, with the enforced controls in this tree.** It uses a one-use, tenant-owned bootstrap authorization, a fresh server-assigned endpoint ID, a separate expiring credential, explicit human approval before work, server-side credential/replay checks, and protected Windows state. Do not weaken these boundaries to simplify the demo. The local enrollment overwrite race was closed in this working tree; the elevated Windows run is still required.

## Additional boundary checks

- **Credentials and logs:** The human bootstrap password uses a hidden prompt and is created atomically only if no human user exists (`backend/cli.py:51-96,223-231`). Issued enrollment secrets are returned once with `Cache-Control: no-store` (`backend/api/human_control_plane.py:228-254`); endpoint credentials use the fast verifier only for generated high-entropy values (`backend/application/enrollment/service.py:144-154,240-252`). Database initialization logs type or exception class, never the connection URL (`backend/core/database/database.py:60-64,145-147,177-179,195`). API request logs include method and path, not headers or query strings (`backend/api/main.py:207-242`); agent CLI failures print error codes rather than remote response bodies (`backend/agent/__main__.py:140-143`).
- **Agent message replay:** Agent message IDs are claimed in SQL after authentication and authorization, before handler invocation (`backend/application/agent/processor.py:129-155`; `backend/infrastructure/persistence/sqlalchemy_replay_guard.py:13-43`). This is separate from the one-use bootstrap claim. Persisting the claim prevents simple replay across a process restart until the protocol expiry window.
- **Personal scanner:** The compatibility launcher binds the legacy backend to loopback and opts into legacy routes only for local development (`run.py:145-161`; `tests/unit/test_personal_launcher_safety.py:6`). The personal scanner's separate pre-mission working-tree diff was preserved rather than rewritten for this mission. The characterization tests establish only the covered local behavior; they are not proof of every historical scanner output.
- **Tenant attribution:** The organization comes from the redeemed authorization and is compared again in the SQL transaction (`backend/application/enrollment/service.py:118-154`; `backend/infrastructure/persistence/sqlalchemy_enrollment_repository.py:111-125`). Capability claims start as `unverified` metadata (`backend/application/enrollment/service.py:141`), so they are not an authorization basis.
- **Human token administration:** Issuance, listing, and revocation require a human `OrganizationContext` plus the relevant enrollment permission (`backend/application/enrollment/tenant_service.py:19-60`). Token lifetime is 1–1440 minutes and `max_uses` is fixed at one (`backend/application/enrollment/tenant_service.py:22-24`; `backend/api/human_control_plane.py:241-254`). The list marks an unused token expired when server time reaches its deadline (`backend/api/human_control_plane.py:823-835`).

## Final acceptance record

1. Final backend: 536 passed, one directory-symlink skip, one SQLAlchemy warning, 58.01 seconds. Final portal build/typecheck passed; three browser tests passed in 9.5 seconds. Dependency audit reports zero known frontend vulnerabilities.
2. Installer discovery, exact CA-byte fingerprint binding, no-overwrite storage and concurrent terminal regressions passed. Both PowerShell scripts parse. Fresh minimal server/agent Python 3.11 runtime smoke checks passed. Elevated Program Files/ProgramData installation and ordinary-user denial remain pending.
3. The Omen isolated strict-HTTPS golden path passed with actual read-only Windows execution and honest BitLocker failure coverage. Physical LAN/firewall, installed SYSTEM task, notebook scans and restart checks remain pending.
4. No default-port LM Studio/Ollama process/listener was detected. Live inference memory/latency is unverified; AI stays disabled by default and provider-failure behavior has automated coverage.

See [the implementation acceptance record](../operations/OCTOBER15_ACCEPTANCE.md) and [progress log](../DEMO_PROGRESS.md) for measured outcomes and physical rehearsal checks. The base commit does not identify every uncommitted shared-tree change; preserve source ownership when preparing a later commit.

Agent credentials authenticate possession of the enrolled endpoint's credential. Hostname and capability metadata do not provide hardware attestation, and a compromised approved endpoint can falsify its own findings. Physical identity approval and protected endpoint installation are part of the pilot's trust assumptions; stronger attestation is outside this design.

**Implementation boundary:** No remote remediation route is mounted by the production app, and the new agent executes only allowlisted read-only checks. Any proposal to expose remediation, trust agent capability claims for authorization, enable wildcard CORS, run LAN HTTP, or place credentials in user-readable storage requires a new security review.
