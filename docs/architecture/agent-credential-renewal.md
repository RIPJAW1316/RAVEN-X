# Agent Credential Auto-Renewal Architecture (WS-01)

## Overview

Windows endpoint agents enroll with a 30-day opaque bearer credential stored in
`%ProgramData%\RavenX\agent\credential.bin` under machine-scope DPAPI
(`CRYPTPROTECT_LOCAL_MACHINE`) and a verified `SYSTEM`/`Administrators` DACL.

WS-01 adds automatic, crash-safe, revocation-aware credential renewal. The
agent generates the successor credential and stores it under the same
protections **before** the control plane commits any lineage change. The server
stores only a verifier, records exactly one successor per predecessor, and
fixes the predecessor's remaining authority at first commit. Recovery never
depends on receiving a particular HTTP response inside a short grace window.

This document is the contract for the Round 2 protocol. It replaces the
Round 1 design in which the server minted a secret that existed only in the
HTTP response and revoked an unconfirmed successor on every predecessor retry.

---

## Security Properties

1. **Active endpoint and tenant eligibility only**
   - Ordinary authentication, work polling, message submission, renewal, and
     confirmation all share `_authenticate_agent`.
   - `OrganizationStatus.REVOKED` is rejected with HTTP `401`
     (`authentication_failed`) before any secret comparison.
   - `OrganizationStatus.SUSPENDED` is reported with HTTP `403`
     (`endpoint_not_active`) only after possession of a currently usable
     credential is proven, so suspension is not an unauthenticated oracle.
   - A missing organization record fails closed (`401`).
   - Endpoints in `NEW` / `DEGRADED` / `OFFLINE` cannot renew (`403`,
     `endpoint_not_active`). `REVOKED` endpoints are `401`.
2. **Earned identity attribution**
   - `credential_id`, `endpoint_id`, and `organization_id` are taken from
     persisted records. Client-supplied identity that disagrees is `401`.
3. **Replay and clock-skew protection**
   - `/api/v1/agent/renew` and `/api/v1/agent/renew/confirm` carry a UUID
     `message_id`, UTC `timestamp`, `nonce`, and `protocol_version`.
   - Requests outside the 5-minute skew window are `400`
     (`stale_or_future_message`).
   - Replayed `message_id` values are `409` (`replayed_message`).
   - Logical renewal idempotency is **not** keyed by `message_id`. It is
     keyed by `(predecessor_credential_id, successor_credential_id)` plus
     possession of the successor secret.
4. **Tenant-attributed audit without secret leakage**
   - Rotation, renewal, confirmation, revocation, authentication failure,
     authorization denial, and replay rejection record `organization_id` and
     `endpoint_id`.
   - Raw secrets are redacted in `repr()`, `str()`, and `to_dict()`. The
     renewal receipt never contains credential material.

## Protocol Design

### 1. Credential generation and ownership

The agent generates both the successor identifier (`CredentialId.new()`) and
the successor secret (`secrets.token_urlsafe(32)`) locally. The server never
issues a renewal secret.

The server stores a keyed verifier, `token-hmac-v2`, not an unkeyed
`hash_token(successor_secret)`. The verifier is
`HMAC-SHA256(server_key, salt || credential_id || secret)`. The server key
never enters the credential row. The HTTP response is a lineage receipt:
successor id, predecessor id, successor expiry, and the immutable
`predecessor_valid_until`. It contains no secret.

Enrollment and administrative rotation remain `token-sha256-v1` because those
secrets are generated by the server. Verification still accepts that legacy
form. A lost HTTP response still recovers: the agent keeps the successor
secret in `renewal.bin`, and the server keeps the salt and the same key.

Administrative `rotate_credential` remains a privileged control-plane action.
It still mints a server-side secret, grants no overlap, and is not exposed as
an unauthenticated agent API.

### 2. What is durably stored on the agent

| Stage | `credential.bin` (version 1) | `renewal.bin` (additive) |
| --- | --- | --- |
| CURRENT | Usable predecessor | Absent |
| PREPARED | Unchanged predecessor | Agent-generated successor, written and verified **before** any request |
| PROMOTED | Successor (same version-1 schema) | Removed (a leftover naming the current credential is discarded) |

Both files are DPAPI-protected, ACL-verified, and written with temp-file /
`os.replace` semantics. `credential.bin` keeps the version-1 document so an
older agent can still read it after a rollback; older agents ignore
`renewal.bin`.

### 3. Idempotency keys and safe retries

A renewal is identified by the pair
`(predecessor_credential_id → successor_credential_id)`.

- Same successor id **and** same successor secret: return the committed
  lineage. `predecessor_valid_until` and successor expiry are not rewritten.
- Same successor id and a **different** secret: `409` `renewal_conflict`.
- Different successor id for an already-renewed predecessor: `409`
  `renewal_conflict`. The first successor is never revoked.
- Distinct `message_id` values are required for replay protection; they do
  not create a new lineage.

The agent prepares `renewal.bin` once and never overwrites it. Concurrent
retries therefore propose the same successor.

### 4. Server transaction and concurrency

`renew_credential` runs inside `begin_serialized_write` (`BEGIN IMMEDIATE`)
with row locks on the endpoint and predecessor.

1. Re-check endpoint `ACTIVE` and predecessor usability at `now`.
2. If a `endpoint_credential_renewals` row already exists for the
   predecessor, return `EXISTING` or `CONFLICT`. The row is not updated.
3. Otherwise require the predecessor to still be `ACTIVE` and inside the
   renewal window (`expires_at - now ≤ 10 days`).
4. Insert the successor credential, mark the predecessor `ROTATED`, and
   insert the lineage row with
   `predecessor_valid_until = min(now + 15 minutes, predecessor.expires_at)`.

Database invariants:

- `successor_credential_id` is the primary key.
- `predecessor_credential_id` is unique.
- `successor_credential_id <> predecessor_credential_id`.

A racing second insert hits `IntegrityError` and is reported as `CONFLICT`.
One `ACTIVE` credential per endpoint is necessary; the unique predecessor
constraint is what prevents a retry from minting a second successor.

### 5. Client acceptance of delayed or duplicate responses

`WindowsAgentStateStore.promote_renewal`:

- Accepts a receipt only when it names the prepared successor of the current
  stored credential.
- Is a no-op if that successor is already current.
- Rejects any other successor without changing disk state.

A delayed response A that arrives after response B therefore cannot overwrite
newer valid local state. An in-flight request that lands after local
promotion is an idempotent `EXISTING` on the server and a no-op on the agent.

### 6. Recovery after crashes

| Failure | Recovery |
| --- | --- |
| Lost HTTP response after server commit | `renewal.bin` still holds the successor. A retry with the predecessor is idempotent while the predecessor window is open. After that window, or after natural predecessor expiry, the agent probes `/renew/confirm` with the prepared successor and promotes on success. |
| Client powered off after server commit, before `credential.bin` replace | Same: `renewal.bin` survives reboot. |
| Crash after promotion, before confirmation | The next authenticated request that presents the successor (`/messages`, `/work`, or `/renew/confirm`) confirms the lineage and permanently closes the predecessor. |
| Server restart between prepare / issue / confirm | Lineage lives in SQLite. A new process on the same database returns `EXISTING` or accepts the successor probe. |
| Prepare succeeded, request never reached the server | Predecessor is still `ACTIVE`. Retry proposes the same successor. |
| Outage across the predecessor's natural expiry, successor never committed | Agent never presents the expired predecessor. The successor probe fails `401`. Operator re-enrollment is required. |
| DPAPI or ACL failure during prepare | `credential.bin` is untouched; `renewal.bin` is not created. |
| DPAPI or ACL failure during promote | `credential.bin` is rolled back to the predecessor; `renewal.bin` is kept. |

### 7. Expiry, immutable grace, revocation, confirmation

- A credential is usable while `ACTIVE` and unexpired, or while `ROTATED`
  with an open, unexpired predecessor window.
- `predecessor_valid_until` is written once and never extended. Retries at
  minutes 0, 1, and 14 return the same deadline. Minute 15 rejects the
  predecessor.
- Confirmation (explicit `/renew/confirm` or first successful use of the
  successor) sets `confirmed_at` and `predecessor_closed_at`. Those fields
  are never cleared. Grace is not reopened.
- Administrative credential, endpoint, or organization revocation is
  immediate. Revoking an unconfirmed predecessor also revokes its successor.
  Revoking either side closes the predecessor window.
- Expired credentials are never accepted as a recovery shortcut.

### 8. Backward compatibility with version-1 agent state

`credential.bin` remains `{version: 1, endpoint_id, credential_id,
credential_secret, organization_id, protocol_version, credential_expires_at,
server_url, ca_sha256}`. An older agent can load a post-renewal file. A
current agent can load a file written by the installed agent at
`fc9d3c38` and then prepare `renewal.bin`.

### 9. Database migration

A new table `endpoint_credential_renewals` is additive. Existing
`endpoint_credentials` columns are unchanged. `DatabaseManager.create_tables()`
(`Base.metadata.create_all`) creates the table on the next process start.
No backfill is required: there is no committed production renewal lineage
on this branch. The unique predecessor constraint is the cutover invariant.
There is no Alembic revision in this prototype; applying the table is the
entire migration.

### 10. Stolen predecessor authority is bounded

A holder of a usable predecessor can mint **at most one** successor, and
only during the last 10 days of that predecessor's life. After confirmation
or `predecessor_valid_until`, the predecessor is dead. A second successor
for the same predecessor is a conflict, not a rotation. Immediate
administrative revocation still wins. Unlimited rolling authority would
require continuous possession of each new successor **and** remaining
inside that successor's own later renewal window.

## State machines

### Server

```
[C_old ACTIVE]
   │
   │ POST /api/v1/agent/renew
   │   authenticated with C_old
   │   body names agent-prepared (C_new_id, C_new_secret)
   ▼
[C_old ROTATED, predecessor_valid_until fixed]
[C_new ACTIVE, unconfirmed]
   │
   ├── same (C_new_id, C_new_secret) retry → EXISTING, no writes
   ├── different successor                 → CONFLICT, C_new kept
   ├── /renew/confirm or first use of C_new
   │     → confirmed_at, predecessor_closed_at; C_old permanently invalid
   └── endpoint / credential / organization revocation
         → both sides immediately invalid
```

### Windows agent (`CredentialRenewalCoordinator`)

1. CURRENT and outside the 7-day threshold: no network.
2. CURRENT and inside the threshold: write `renewal.bin`, then propose.
3. PREPARED and stored credential unexpired: `POST /renew` with that
   successor. A receipt naming it promotes. `authentication_failed` falls
   through to the successor probe.
4. PREPARED and stored credential rejected or expired: `POST /renew/confirm`
   with the prepared successor. Success promotes. Dual `401` requires
   operator re-enrollment.
5. Transient failures leave `renewal.bin` untouched.

`.renewal.lock` is an OS exclusive lock (`msvcrt.locking` / `fcntl.flock`)
on a persistent, never-deleted file. Ownership is the open handle. The
kernel releases it when the owner exits. Age is never used to reclaim a
live owner's lock. A releasing process never unlinks the file, so it
cannot delete a successor's lock.

## HTTP surface

| Method | Path | Auth | Body | Success |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/agent/renew` | Predecessor bearer | successor id + secret, `message_id`, timestamp, nonce | Lineage receipt, no secret |
| POST | `/api/v1/agent/renew/confirm` | Successor bearer | successor id, optional predecessor id | Confirmation + successor expiry |

Shared mappings: `401` authentication / revoked tenant; `403` suspended
tenant or endpoint not active; `409` replay / conflict / not due; `400`
skew; `422` malformed proposal.

## Round 3 — Compromise, rollback, keyed verifiers, and durability

### Credential-compromise revocation

`rotate_credential` replaces one ACTIVE credential. It is administrative
rotation, not containment.

`revoke_credential` and `revoke_compromised_credential` always walk the
same-endpoint successor chain, including confirmed descendants. Historical
rows remain. Audit events `credential.revoked` and `credential.lineage_revoked`
carry organization attribution and no secrets. Cross-endpoint and
cross-organization credentials are untouched.

A confirmed successor of a revoked predecessor is unauthorized for
messages, work, confirmation, and further renewal.

### Supported upgrade and rollback matrix

| Fleet state | Pre-WS-01 binary (schema 1) | WS-01-compatible binary (schema 2) |
| --- | --- | --- |
| Old server + old agent, never renewed | Allowed | Allowed after `apply_sqlite_migrations` |
| Server upgraded, old agent still on enrollment secret | Allowed to stay; agent authenticates with `token-sha256-v1` | Supported |
| Agent upgraded and renewed | Refused | Supported |
| Rollback before any renewal | Allowed if the current database is kept | n/a |
| Rollback after confirmation while HMAC successors are ACTIVE | Refused (`incompatible_hmac_successors`) | Keep this binary |
| Rollback during committed-but-unconfirmed renewal | Refused (`pending_renewal_lineage`) | Keep this binary |
| Lost HTTP receipt, then rollback | Refused | Retry `/renew` then `/renew/confirm` |
| Restore an older database backup missing live credential ids | Refused | Keep the live database |
| Empty or missing schema-version metadata while HMAC or renewal rows exist | Refused (`ambiguous_schema`) | Do not treat the database as schema 1 |
| Backup whose credential ids match but status, lineage, revocation history, or verifier-key identity does not | Refused | Reviewed recovery; this check does not restore |
| `rollback-check` against a missing database file | Refused (`missing_database`) | The command must not create the file |

`backend.cli rollback-check` copies an existing SQLite file, and its WAL if
one is present, into a private owned snapshot directory. Every ancestor is
refused when an untrusted principal has an effective delete, rename, or
reparse right, and a reparse point is not followed. The copy is created
through an open directory handle with a private access list at creation, so
a later rename of the path does not redirect the bytes. SQLite may create
`-shm` inside the snapshot. The source database, WAL, and SHM are not modified.
The snapshot is removed through the directory handle that created it, including
its marker and database files. The handle stays open until that removal finishes.
A pathname that was replaced is not deleted. If removal is unsafe, the command
exits `4`, names the `ravenx-rollback-*` directory, and tells the operator to
confirm that the directory is owned by the operator and grants access only to
that user, SYSTEM, and Administrators before deleting it by hand. Ancestors
must be owned by the operator, SYSTEM, Administrators, LocalService,
NetworkService, or TrustedInstaller, and must not grant any other principal
delete, delete-child, write-DACL, write-owner, or generic write. A capability
SID with only traverse or list rights is not a substitution right. One with
effective full control is refused. An access entry that this process cannot
decode, including a callback ACE, is also refused. No path is trusted after
an incomplete access-list inspection.

The ordinary Windows profile used in the Round 9 review is an unsupported
snapshot location. Its ancestry includes a capability SID with effective full
control, and the suite on that profile was 713 passed, 40 failed, and 3
skipped. Those failures are the storage policy refusing the profile. They are
not a reason to add that SID to the allowlist, and they are separate from the
renewal, tenant, replay, and TLS tests. A disposable protected profile on the
same review passed 753 tests and skipped 3. This project does not claim that
every ordinary profile can host snapshots, and it does not change a profile's
existing access lists.

`RAVENX_ROLLBACK_SNAPSHOT_ROOT` selects only the rollback snapshot directory.
It is not a verifier-key setting, and it is not required on every host.
Verifier-key publication uses the database directory, the sidecar or
environment key, and that directory's own access list and parent checks. A
key can be published in a protected database directory while this variable is
unset. Rollback inspection uses the default
`%LOCALAPPDATA%\RAVEN-X\rollback-snapshots` directory only when every ancestor
of that directory passes the storage policy. The ordinary profile examined in
the Round 9 review does not pass: a capability SID there has effective full
control, so that default directory is an unsupported snapshot location. On
such a host, set `RAVENX_ROLLBACK_SNAPSHOT_ROOT` to a separate directory
created for RAVEN-X and checked before use. Every ancestor must be owned by
the operator, SYSTEM, Administrators, LocalService, NetworkService, or
TrustedInstaller. No ancestor may be a reparse point. No ancestor may grant
any other principal delete, delete-child, write-DACL, write-owner, generic
write, or generic all. If the chosen snapshot directory fails those checks,
rollback inspection stops. The process temp folder is never used as a
substitute. A killed inspection may
leave that protected directory behind; there is no broad cleanup.
Exit `0` means compatible, exit `3` means refused, and exit `4` means the
inspection itself failed. It does not call `create_tables`.
A downgrade is not `already_compatible` until active `token-hmac-v2`
credentials and open renewal lineages have been checked. Missing, empty, or
inconsistent version metadata with those rows is `ambiguous_schema`.

Matching credential identifiers is not enough to approve a backup. The restore
decision also requires the same status, endpoint, organization, verifier-key
identity, pending lineage, confirmed lineage, and revocation history. A
caller-supplied completeness flag is not that evidence. Uncertain freshness is
a refusal. `evaluate_database_restore` does not write a database.

Supported rollback is a code rollback of a database that still has no open
lineage and no active HMAC successor, after `rollback-check` returns
`code_rollback_safe`. Unsupported: rolling a pre-WS-01 binary onto active HMAC
successors, unconfirmed lineages, ambiguous version metadata, or a backup that
would resurrect a revoked credential.

Never restore an older backup when agents may already hold newer secrets.
Never overwrite the live database. The upgrade scripts in `scripts/` plan a
disposable tree only. `-Execute` is refused. They are not a production
upgrader; that work is WS-03.

The supported upgrade boundary is `0.5.0-ws01`. Arbitrary older binaries are
not a recovery mechanism for HMAC successors or unconfirmed lineages.

### Windows prepared-state durability

Publication writes a temporary encrypted file, then publishes `renewal.bin`.
The published **file** flush is required before every proposal, including a
retry that finds `renewal.bin` already written. Decrypting that file is not a
durability check. While the required flush fails, no renewal request is sent
and the same successor stays in place. A single valid `renewal.bin.*.tmp`
orphan that matches the current identity can be recovered. Two different valid
successors are left for an operator. Foreign or corrupt temps are left in place.

Parent-directory metadata is not the same guarantee. Windows commonly refuses
`FlushFileBuffers` on the directory handle. That failure is reported as
`ntfs_directory_metadata_not_flushable`. It is not counted as a successful
flush, and it is not papered over by ignoring a required file error. Directory
durability and storage-cache power-loss behavior remain an isolated physical
validation gate. Do not run that gate on the owner's main HP Omen, and do not
describe a successful file flush as physical power-loss durability.

SQLite on the control plane uses WAL and `synchronous=FULL` on both the sync
and async engines. FULL waits for the commit's WAL frames to be flushed to the
operating system. It improves transaction durability compared with `NORMAL`.
It does not, by itself, prove hardware power-loss safety.

### HMAC verifier-key custody

Successor verifiers are
`token-hmac-v2$salt$mac = HMAC-SHA256(server_key, salt || binding || secret)`.
The key is 32 bytes from `RAVENX_CREDENTIAL_VERIFIER_KEY` or from
`credential-hmac.key` beside the SQLite file. It is never stored in a
credential row and must never be logged.

The database stores only `sha256(key)` in `ravenx_verifier_keys`. Startup
binds that key before the API logs ready. A missing sidecar is not recreated
when active HMAC credentials or an existing identity are present. A replaced
file, a different environment key, or a restored database whose identity does
not match the configured key fails startup before HTTP readiness. An empty
database may bootstrap a new key once and record its identity. Every
file-backed database, including development, uses that sidecar. An ephemeral
key is allowed only for an explicit in-memory test database. The published key
file is not deleted if a later step fails, because another process may already
have bound it. Bootstrap takes an exclusive lock on a file created through
the open parent-directory handle. If that path no longer names the same
directory object, startup fails before the key is published. The file contents
are re-read and checked for a complete 32-byte value before the identity row
is committed.

Back up the key file with the database. There is no automatic rotation: a new
key cannot verify existing HMAC credentials. If the key is lost, do not start
with a generated replacement. Revoke the affected credentials and re-enroll,
or restore the original key that matches the stored identity. On Windows the
new key file is restricted to SYSTEM and Administrators; that ACL change
requires elevation. A failure to protect the file deletes the new key and
aborts. That ACL step has not been qualified on the live Omen service account.

### Client-chosen successor entropy

Length and charset checks do not prove entropy. Enrollment and administrative
rotation remain `token-sha256-v1` because those secrets are server-generated.
A lost HTTP response still recovers: the agent keeps the secret in
`renewal.bin` and the server keeps the salt and the same key.

### Approved trust versus presence

`ACTIVE`, `DEGRADED`, and `OFFLINE` are previously approved endpoint trust.
Presence is operational. Confirmation is allowed for approved trust. `NEW`
cannot confirm. Renewal, work dispatch, and assessment results remain
`ACTIVE`-only. `REVOKED` remains an authentication failure.

### Replay retention

Accepted freshness is ±`max_clock_skew` (default 5 minutes). Replay claims
are retained for `2 × max_clock_skew + 60s` (default 11 minutes) so a
future-dated accepted message cannot be replayed after the first skew
interval elapses.
